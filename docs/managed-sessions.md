# Managed browser sessions

This optional Auth source slice adds `lenso.auth.managed-session@1`, Descriptor
1.0.0, and a removable `lenso.auth.session-renewal` HTTP adapter. Account owns
policy, state and atomic credential rotation. Kernel has no session or database
model; Relay selects target-private storage attachments without rewriting Auth
business configuration. This source follows Auth 699bd96 plus storage-reference
281134a. The separate storage-reference candidate remains frozen.

## Explicit configuration and binding

`AccountAuthConfig.managed_sessions` defaults to null. Enabling it requires all
three finite durations and two nonempty canonical caller allowlists:

```json
{
  "managed_sessions": {
    "policy": {
      "idle_timeout_seconds": 86400,
      "absolute_timeout_seconds": 2592000,
      "renew_interval_seconds": 3600
    },
    "issue_callers": ["lenso.auth.password/password"],
    "renew_callers": ["lenso.auth.session-renewal/renewal"]
  }
}
```

These are illustrative synthetic policies, not production configuration changes.
Ordinary Accounts permit at most 30 days idle and 90 days absolute. An operators
Account, selected explicitly by its management session ceiling, permits at most
one hour idle and 12 hours absolute. Operators and ordinary users bind separate
Account Instances with separate fixed policies. Neither a browser nor a renewal
request chooses a profile, TTL, subject, audience or management ceiling. Renewal
interval must be positive and no more than half the initial idle duration.

Password `managed_sessions` defaults to false. In explicit managed mode it binds
the named `managed_sessions` requirement to the same Account's new capability;
the compatible v1 lifecycle uses a ManyPort and rejects more than one binding,
or zero bindings when enabled, before storage I/O. Its verified login subject,
fixed user/password authority and configured audience go to `issue_managed`.
The old issuer requirement remains required and unchanged. Legacy mode retains
the caller's original absolute expiry and never becomes managed implicitly.
Old Password response shapes remain unchanged; the renewal adapter's read-only
state endpoint supplies initial server renewal metadata after login.

## Durable transitions

`issue_managed` freezes the original absolute deadline, idle duration and renewal
interval in Account's private metadata table. `renew` accepts only an opaque
session credential. PostgreSQL locks subject then session and reads the database
clock after locks. D1 executes a guarded atomic primary batch. Active subject,
current credential, revocation, idle and absolute deadlines and minimum interval
must all hold. Current policy can narrow eligibility and expiry, but cannot widen
the issued envelope. Delegated and legacy sessions cannot renew. Authentication
remains read-only and enforces current managed policy without refreshing expiry.

Exactly one concurrent request with the current credential rotates it. Losers
receive `StaleCredential`; they cannot revoke the winner. Only digests are stored.
Old digests cannot authenticate or renew, but their history maps to the original
stable session ID for logout through the existing `revoke_credential`. Trusted
logout adapters retain their fixed issuer binding, selected ingress credential
and POST/CSRF admission; historical credentials are never accepted as authority
for authentication. Delegated children retain their original expiry and stable
parent reference; parent revocation still invalidates them. New grants clip their
actual stored and returned expiry to the effective parent deadline inside the
admitting transaction or primary batch. CredentialState and scoped receipts
apply the same current-policy bounds, without refreshing expiry.

`read_managed` is read-only, uses the same current-policy checks and renew caller
allowlist, and returns dates/session ID without credential material. It allows
reading before the renewal interval has elapsed. Existing Auth, CredentialIssuer
1.1, session, delegation and credential-state operations keep their public
contracts. No existing Role snapshot is regenerated by this change.

History retention is bounded by the finite absolute lifespan and minimum renewal
interval of each session. This first version does not purge history. Any later
explicit maintenance must preserve history for live sessions and logout/revocation
semantics; never remove live history merely to make a stale request succeed.

## Browser contract

The removable adapter provides POST `/auth/session/renew` and GET
`/auth/session/state`. Ingress owns unambiguous credential extraction and CSRF
admission before POST reaches the adapter. Configure one exact HTTPS origin and
distinct `__Host-` session/CSRF cookie names. The adapter never parses raw Cookies
or accepts credential, profile or authority from a request body. Read requests
without an Origin require a same-origin Fetch Metadata header. See the adapter
README and its tested browser module for exact admission and Cookie details.

Only a successful rotation writes new Secure, HttpOnly session and Secure CSRF
Cookies, both Path=/ and SameSite=Lax, with the server idle expiry and no-store.
Every failure returns zero Set-Cookie headers. HTTP409 stale is retryable
competition and must never clear Cookies or initiate server logout. The supplied
browser helper uses Web Locks for browser-wide single flight; it validates the
current Cookie at most once after stale or unknown response delivery. The owning
application broadcasts fresh metadata to its tabs and schedules only active
sessions. It never automatically replays authentication-side business actions.

If the server commits rotation but its successful Cookie response is lost, an
old credential cannot recover the random replacement from a digest ledger. One
read-only validation detects this and the user must sign in again. This limitation
is tested and is not presented as seamless response-loss recovery.

## Explicit migrations and validation

PostgreSQL migration 6 and D1 migration 3 add managed metadata and digest history.
Old migration SQL is unchanged. Operators must explicitly setup/upgrade a dedicated
database; Account activation verifies readiness and never auto-migrates. Legacy instances with managed policy disabled continue to verify the exact PG5
or D1v2 history and use the original SQL without the new tables. Opting in requires
explicit `setup_managed` / `upgrade_managed` (PG6 / D1v3) before Ready. Already
upgraded instances retain digest-history logout even when managed policy is later
disabled; schema support is verified independently of configuration. There is no production migration/deployment
in this candidate. Password storage and migrations remain unchanged.

Focused Native tests run the actual PostgreSQL Store in a fresh isolated cluster;
local workerd tests compile actual Account Rust D1 SQL and the owner bridge into
an independent fixture. Both cover concurrent rotation, replay, historic logout,
revocation/disable races, idle/absolute expiry, policy narrowing, original issuer
compatibility and restart. The D1 fixture's independent wasm-bindgen transport
cohort is disclosed; it is not a substitute for direct candidate Native/Workers
checks against the unchanged declared cohort. Generated-client routing, HTTP
Cookie/Origin composition and browser concurrency have separate synthetic gates.
The separate `experiments/managed-session-app` fixture runs actual Account,
Password, renewal adapter and generated clients through Registry Kernel 0.3.12,
Ingress 0.4.11 and nominal HTTP 0.3.7 on Native PostgreSQL and local Workers D1.
Real CSRF admission, caller isolation, Cookie competition, policy narrowing,
response loss and replay are synthetic App acceptance gates in candidate CI.
Declare the new stateless renewal adapter as native authoring v2 and bind its
named `managed_sessions` requirement; declaring it as legacy v1 is invalid Host
assembly. The Workers fixture provides only public RuntimeDriver spawn/timer
mechanics and does not qualify the older Registry WorkersDriver package.
Full remote candidate CI, production Host qualification and Relay/Console page
integration remain parent-owned gates. No production deployment is authorized.
