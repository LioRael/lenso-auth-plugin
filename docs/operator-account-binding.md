# First operator binding candidate

Auth is the sole writer. This independent local candidate extends frozen renewal `a5abf5df426eaa78a594e75e90687c820bca312e`; it authorizes source and synthetic acceptance only.

## Relay contract and responsibilities

`lenso.auth.operator-session@1`, provider `lenso.auth.operator-session`, is a stateless authoring-v2 workflow. Its operations are `bootstrap_binding {}`, `read_binding {}`, `exchange_session {}`, `revoke_binding { binding_id }`, and `recover_revocation { binding_id }`. Each request is closed: callers cannot select realm, subject, grants, TTL, audience or claims. Bootstrap/read/exchange/recovery derive the accounts subject from a verified sealed accounts user assertion and live accounts CredentialState. Bootstrap additionally requires an exact configured local owner caller, an explicitly confirmed accounts subject, and a window no longer than fifteen minutes. Registration or ordinary login cannot grant operator access.

Relay owns HTTP credential extraction, Origin/CSRF admission, owner confirmation UI, Cookie creation/clearing and login into the operators workspace. It wires the exact operation audiences into the appropriate accounts/operators login configuration and binds the workflow's named ports: `bindings`, `accounts_state`, `operators_state`, `operators_issuer`, `access`, `access_admin`, `audit`. Two CredentialState ports refer to distinct Account instances. Every privileged product operation must check current CredentialState, both signed and current management ceiling, and live scoped Access permission. Checking only assertion permissions and Access does not apply a configuration change that narrows the current ceiling.

The exchange issues an independent finite operators credential using the existing distinct operators Account issuer, public key and existing Secrets provisioning. Issuers and keys must differ. The credential uses configured audiences, the subset of configured business permissions currently allowed by Access, and a fixed TTL of at most one hour. Source account disable blocks it through a live Directory check. Source session logout/expiry does not revoke an already issued operators credential; it is independent realm login, not a delegated child session. Relay must distinguish logout of the current identity from logout of all identities in this browser/device. All-identities logout invokes the existing `lenso.auth.credential-issuer@1` `revoke_credential { scheme: "session", credential }` separately on accounts and operators (or `revoke { session_id }` only for a verified session reference), confirms durable results, then clears the respective Cookies. A revoked binding permanently removes operator eligibility and is not ordinary logout. An unknown/failed revoke must not be displayed as complete logout. Serialize identity exchange/logout, invalidate in-flight responses and reject late Cookie writes, so a concurrent exchange cannot restore an identity after the all-identities logout UI has completed. Do not expose the existing issuer issuance operations publicly through the logout route; Host caller/operation admission must remain narrow. Exchange currently uses the existing CredentialIssuer, not automatic managed-session issuance.

## Account state and collaboration

`lenso.auth.operator-binding@1` is an Account-owned private role: `prepare_bootstrap`, `activate_binding`, `read_binding`, `revoke_binding`, `prepare_recovery`, `complete_revocation`. Only configured canonical workflow instances can call it. The opt-in operators Account also binds exactly one `source_accounts` Directory whose canonical instance equals configured `source_account_instance`; source accounts do not depend on operators, preserving the DAG.

Account owns a private binding table: source issuer/subject, deployment and scope, generated operators subject, revision, pending/active/revoked status, grant audit event and Access policy revision, and durable revocation intent/actor/time/audit receipt. Mapping uses stable source issuer plus source subject plus deployment, never email or display-name matching. Existing identities, sessions, issuers and original storage remain authoritative. No generic database model enters Kernel or Relay.

The workflow appends requested audit, prepares pending binding, verifies a five-second internal operators assertion, bootstraps the existing Access protected role for this exact scope, creates one explicit finite business/login role, assigns it, appends applied audit, then activates binding last. The protected role grants existing Access roles/bindings management only. The internal assertion comes from the existing Account signing authority, is limited to the three required Access admin operations, and is never returned to browser or Relay. Scope/source echoes are verified before use. No cross-Auth/Access atomic transaction is claimed. Partial grants remain unusable while binding is pending; retry is allowed only within the configured bootstrap window. Transfer/rebinding requires a separate explicit owner operation.

Both issuance paths, Auth, CredentialState, managed read and renew check binding status/revision and live source account status. Removing the optional binding configuration also rejects historical binding claims. Caller-supplied binding claims are rejected; Account injects them. Fixed management ceilings bound requested permission claims on both issuance paths. Existing managed stale responses remain classified before and after a concurrent rotation race.

Revoke requires a live operators assertion, matching signed/current deployment and scope ceilings, and live Access binding-management permission. Account writes revoked status, increments revision and records immutable actor/time plus pending revocation intent before Access cleanup/audit. Failures leave credentials denied. Role cleanup that is already absent is successful. An audit receipt is acknowledged with revision CAS; the binding remains revoked. The Access protected last-admin role is not removed automatically.

Recovery requires the exact local owner caller and the live, confirmed source bootstrap account. It can run after the bootstrap window: an internal five-second assertion has only `revoke_role` audience and can finish cleanup and append the original revoker/time with recovery actor metadata. Completion cannot activate or grant a binding. Audit append does not promise cross-plugin exactly-once delivery: failure between append and receipt acknowledgement can create a duplicate event on explicit recovery.

## Compatibility and qualification

Ordinary accounts remain opt-out at the business configuration level. **Host assembly migration is required for this Account release:** the new legacy many-port Directory requirement must have an explicit provider selector. Disabled binding mode selects a declared empty optional source Slot; enabled mode selects exactly the configured source Account instance. Leaving the old automatic selector unchanged selects Account itself and creates an activation cycle. An empty `HostBinding::to_instances([])` is not an absence selector in AppPlan 0.4.6; use `HostBinding::new(..., "source_accounts")` against a declared empty `HostSlot::optional("source_accounts")`. The independent Workers Host now implements this through the actual owner Descriptor releases and public HostCatalog/PluginRoot resolver; `experiments/operator-binding-workers-app/src/lib.rs::resolve_catalog` is the executable declaration. Relay can use the same selection in its Native/Workers Host, without a Core change or hand-authored replacement Plan. Existing Role snapshots and original SQL are unchanged. New private Account histories are PostgreSQL v7 and D1 v4, applied only through new explicit `setup_operator_bound` / `upgrade_operator_bound` entrypoints. Old setup/upgrade stay at legacy or managed histories. Ready verifies history read-only, requires v7/v4 when bindings are enabled, and otherwise accepts exact verified legacy/managed/operator histories.

The declared Auth Registry cohort is unchanged. Source compiles and strict lint checks cover Native and Workers. Native synthetic acceptance uses actual Kernel 0.3.12, two Account instances, Access PostgreSQL source `94b6d06cff1e6f17a06e771df232f662cae28ad5`, and Audit PostgreSQL source `83b4e52e8c6eaf2bbe5356dccd1e3a59b872c8e9`. Its twelve gates include controlled bootstrap, ordinary-account denial, current source/Access/ceiling checks, real Access/Audit faults, persistent denial and explicit recovery. Kernel supervision closes App admission after plugin faults, so recovery tests restart a fresh App and inspect durable state.

The independent `experiments/operator-binding-workers-app` Host formally locks wasm-bindgen 0.2.127 / js-sys 0.3.104 / wasm-bindgen-futures 0.4.77, matching the exact Access/Audit D1 revisions above. It passes Rust 1.94 locked/offline Wasm check and strict clippy, and **eleven actual workerd App gates** with the real Kernel, two Account instances, AccessD1, AuditD1, actual owner JS facilities and explicit owner migration entrypoints. Actual `PLUGIN_DESCRIPTOR_JSON` releases resolve through public HostCatalog/PluginRoot; assertions prove the empty source Slot, enabled operators exact source Account, disabled operators empty Slot and seven named workflow dependencies. There is no hand-authored replacement Plan, dependency patch/replace, external source override or Core change.

The Workers gates cover controlled bootstrap, ordinary/wrong-owner denial, finite protected/business/login Access grants and persisted Audit before activation, distinct operators realm Auth/Inspect, live login permission, binding feature removal, source disable, current ceiling/scoped permission narrowing, real Audit revocation failure, durable denial and controlled fresh-App recovery, and real applied-Audit/Access-write failures leaving binding pending. The three real SQL fault cases report the domain/outer Runtime outcome, same-App AdmissionClosed and actual shutdown outcome separately. Fresh events create new actual Apps against the same synthetic D1 state; revoked/pending credentials remain denied, and recovery preserves the original revoker without granting login. After source disable, recovery requires a new real source login; reenabling the account does not restore its revoked old session.

Account business configuration uses logical `storage_ref` values `auth/accounts` and `auth/operators`; private D1 attachments must match them, without target-based configuration rewriting. Access/Audit retain their given legacy owner interfaces. The Host implements only mechanical scheduling/timers through the public RuntimeDriver trait; this does not qualify the older Registry WorkersDriver package. Native and Workers fixture graphs are separately qualified; one byte-identical serialized full graph is not claimed. The Auth Root and frozen renewal .128 lock remain untouched. External owners need new revisions only if integration instead insists on retaining .128 across the full graph. Independent D1 model/storage proof remains separately scoped with its own shims/hashes. Relay HTTP Origin/CSRF/Ingress/page assembly and authoritative remote CI remain parent-owned.

Before any real bootstrap/grant, migration or deployment, confirm the actual source account subject, deployment scope and finite permission list. This candidate reads no production credentials or database and performs no remote write, main change, publication or deployment.

## Minimal Relay wiring

Configure the operators Account `operator_bindings` with the fixed source issuer, canonical source Account instance, deployment/scope, confirmed source subject, a RFC3339 bootstrap window of at most fifteen minutes and exact workflow caller. Its management ceiling uses the same deployment and sole resource scope, plus the confirmed finite business permissions. Leave the source Account opted out. Use existing `with_storage_ref` for each Account and retain its existing issuer/key/pepper/assertion-TTL/caller configuration. The Host alone supplies the matching target-private state attachment.

The workflow's closed `OperatorSessionConfig` contains both fixed issuer/public-key pairs, `maximum_assertion_ttl_seconds`, the same `deployment`/`scope_kind`/`scope_id`, confirmed `bootstrap_subject`, exact local `bootstrap_callers`, finite `permissions`, `session_ttl_seconds` (1–3600), and fixed `operator_audience`. Business permissions exclude the reserved operator-login permission. Use `lenso_auth_sdk::audience(role_id, operation)` for operation audiences; accounts login must admit the workflow's accounts-consuming operations, operators login the intended operators operations. The fixture's `plan_with_management` is the complete public synthetic configuration, not a production grant instruction.

Every workflow selector is explicit and includes `.with_requirement_id(port)`:

| Port | Role | Exact provider |
| --- | --- | --- |
| `bindings` | `lenso.auth.operator-binding@1` | operators Account |
| `accounts_state` | `lenso.auth.credential-state@1` | source accounts Account |
| `operators_state` | `lenso.auth.credential-state@1` | operators Account |
| `operators_issuer` | `lenso.auth.credential-issuer@1` | operators Account |
| `access` | `lenso.access-control@1` | operators Access |
| `access_admin` | `lenso.access-control-admin@1` | same Access |
| `audit` | `lenso.audit-log@1` | actual Audit |

Admit the exact workflow in Account CredentialState callers, Access bootstrap callers and Audit writer instances. Relay must keep controlled bootstrap/recovery callers separate from normal login ingress. Source Account selects the declared empty optional `source_accounts` Slot; operators selects that same empty Slot when bindings are disabled and exactly the configured source Account when enabled.
